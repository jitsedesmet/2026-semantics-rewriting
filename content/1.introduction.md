With the finalization of the [RDF 1.2](cite:cites rdf-1-2) and [SPARQL 1.2](cite:cites sparql-1-2) specifications, both data publishers and
queriers will get access to the newly introduced triple term.
RDF 1.2 extends the existing [RDF 1.1](cite:cites spec:rdf-1-1) specification with the addition of triple terms,
which are terms allowed in the object position of a triple that are again a triple.
Allowing for an infinitely deep nesting of triples within the objects of other triples.
This extension to the data model brings native reification modeling to RDF,
and closes the distance between RDF and [Property Graphs](cite:cites iso-gql)
To this end, RDF 1.2's triple term is a clear derivative of what [RDF and SPARQL star](cite:cites hartig2017foundations) introduced over a decade ago.

Even-though RDF 1.2 has native reification modeling support, that does not mean existing,
or new datasets will necessarily model and expose their data using the newly introduced triple terms.
As such, [SPARQL federation](spec:sparqlfed), which allows querying multiple datasets using a single query will need to mitigate between different reification patterns used:
<!-- -->
1. rdf-reification,
2. singleton properties,
3. graph,
4. $$n$$-ary relations, and
5. potentially the vocab introduced by the draft spec [RDF 1.2 interoperability](cite:cites spec:rdf-1-2-interop).
<!-- -->

Since SPARQL 1.2 introduces dedicated syntax to query the introduced triple terms,
functioning as a native reification pattern;
the federated querier would benefit from a dynamic rewriting algorithm where their query, using triple terms over a source that instead uses some reification pattern, would be rewritten to query the reification pattern instead.
To this end, we demonstrate a generic rewriting algorithm that uses SPARQL Construct queries to describe the relation between the various reification schemes and the newly introduced Triple Terms.
