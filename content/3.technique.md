## Query rewriting
{:#technique}

GAV-style mappings consist of a body $$q_\mathcal{S}$$ a query over the existing source,
and a head $$g$$ which is an assertion to be made in the global.
We write the mapping $$ g \rightsquigarrow q_\mathcal{S} $$,
when using SPARQL CONSTRUCT, we refer to the template as the head, and the where clause as the body.
When multiple triple temlates are present in the head, we split the mapping to only contain one triple in the head by writing a union . 
As we mentioned before, only [one mapping can target the global](cite:cites lenzerini2002data),
when many mappings are provided, they are implicity merged using [dataset merge](cite:cites spec:rdf-semantics-1-2), altough for query evaluation,
we perform the bag-union instead of the more expensive set-union.
[](#mapping) shows two example mapping expressed using contruct queries,
and [](#mapping-as-one) shows how we combine those mappings into one having only one triple pattern in the head.

### Algorithm

The generic query rewriting algorithm works by unfolding each triple pattern to the mapping body when the head matches the triple pattern.
When the triple pattern expresses additional constraints,
e.g. the first triple pattern in the query of [](#user-query) constrains the predicate to `rdf:reifies`
and the object to a triple term with predicate `rdf:type`,
the constraints can be _'pushed'_ in the body of the mapping query, leading to optimizations such as shown in [](#rewritten-query) where the `?p` variable is replaced by the desired `rdf:type` predicate.

**Limitations**

Due to the volatile semantics of blank nodes created in the template of a construct query, or the `bnode` expression, we do not support them in the mapping queries,
instead we look to support skolem blank nodes in future work.

As with the general SPARQL federation where one member is used twice in the same query,
blank nodes in the sources are not supported,
and skolomization of the source is a prerequisite [because blank nodes are scoped to the document or result set in which they are serialized](cite:cites sparql-1-2).

We do not support user queries using recursive paths, e.g. `*` and `+`,
we leave support for these paths to future work and suspect recursive SPARQL will be a prerequisite to support those queries.
