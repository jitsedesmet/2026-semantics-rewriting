## Related work
{:#related-work}

Even-though imperative rewriting algorithms could suffice to cover the use-case of
query rewriting between SPARQL 1.2 and SPARQL 1.1 under a given reification scheme,
a generic and declarative approach introduces several advantages:
<!-- -->
1. adaptability to unknown reification scheme, 
2. interpretability of the declarative nature, and
3. reuse of existing skills
<!-- -->
To this end, we will not discuss an imperative algorithm that covers just our bounded use-case,
but instead consult the broader data integration literature.

**Global-as-View**
In the [tradition data integration literature](cite:cites lenzerini2002data), data integration is achieved though describing mappings.
These napping can either:
<!-- -->
1. Describe global view given your local sources (Global-as-Local (GAV)), or
2. describe your local sources given the global view (Local-as-View (LAV)).
<!-- -->

Applying this literature to RDF tends to be tricky.
Applying RDF to this existing data integration literature,
we say that the user writes a query over the _global schema_, while only the _source schemata_ are actually available.
Our goal is to equivalently rewrite the user query such that it targets the source schemata instead of the global schema.
Interestingly, RDF in its most general form is schemaless, meaning the schema is fixed, in relation to relational databases, we could say we have only a single relation, the tripels relation.
Additionally, a basic operation is the [dataset level merge operation](cite:cites spec:rdf-semantics-1-2),
which allows you to seamlessly merge RDF datasets.

In GAV, you describe an element of the global schema with only a single mapping,
while in the case of LAV, you describe each element of each local schema using a single mapping.
This is a source of much confusion, because you can describe the relation of each source to the global using a single query; and this is typically what one would do.
However, the full definition of the mapping towards the global necessitates that you have only one query.
What is implicitly being done, is adding the union operation between all sources; resulting in a single mapping to describe the global.

**RML**

The RDF mapping language, [RML](cite:cites rml) and the standardized Relational to RDF Mapping Language [R2RML](cite:cites spec:r2rml),
both allow you to declaratively describe mappings into RDF.
Each mapping describes the contribution each source provides to the global; again the global mapping is constructed from the individual source contributions by performing the DataSet union operation across the mapped sources.

**RML view**

Traditionally, RML allowed you to describe the contribution of each source to the global under the dataset-union operation.
Recently, [the RML Logical Views module](cite:cites rml-lv, impl-rml-logical-view) has been proposed for the draft [modular RML spec](cite:cites rml-core).
This spec allows the declaration of views ontop of exactly one existing view or source,
or the declaration of views ontop of existing sources 'linked' through the JOIN operation.

To this end, RML remains true to the use case of knowledge graph construction,
but does not allow structural redefinitions over multiple sources.
For example, within RML you cannot express a dataset $$D$$ constructed from dataset $$A, B \text{ and } C$$ such that $$D = (A \cup B) \setminus C$$.


**RML: RDF to RDF**

[POD-QUERY](cite:cites pod-query) enables users to define RDF to RDF mappings within RML.
To this end, the RML mapping description expects a single source (`rml:source`),
as well as a query over that source.
A user query over the global, again constructed as the union of all mappings, can then be rewritten by performing the standard unfolding approach for GAV. 
By expressing the mappings within RML, POD-QUERY inherits the same limitations as RML, namely that only a single source can be used.
Similarly, the reliance on RML forces practitioners to know RML,
while RDF data consumers are typically only familiar with the SPARQL _query_ language.

To this end, our approach allows users to declare their mappings:
<!-- -->
1. over multiple sources (using SPARQL federation)
2. within the practitioner known SPARQL query language
3. using RDF 1.2 as both a target and source

Where support for multiple sources is important in order to allow the expression mappings that go outside of knowledge graph construction to also allow for more complex expressions across sources such as the previous $$D = (A \cup B) \setminus C$$.
