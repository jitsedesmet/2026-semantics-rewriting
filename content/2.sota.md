## Related work
{:#related-work}

An imperative rewriting algorithm could handle a fixed set of reification schemes,
but a declarative approach offers three advantages:
<!-- -->
1. extensibility to reification schemes not foreseen at design time,
2. interpretability of the mappings themselves, and
3. reuse of existing SPARQL querying skills.
<!-- -->
We therefore step back from a hand-written algorithm and draw on the data integration literature.

**Global-as-View**

Data integration is classically framed in terms of mappings between a global schema and local sources[](cite:cites lenzerini2002data).
Mappings can either describe the global schema as a view over the local sources (Global-As-View, GAV)
or describe each local source as a view over the global schema (Local-As-View, LAV).
In both cases, the user writes a query over the global schema, while only the source schemata are actually populated; the system must rewrite the query so that it targets the sources.

RDF opaques this picture in two ways.
First, RDF is schemaless:
in relational terms, every dataset is a single ternary triples relation.
Second, RDF datasets compose naturally through the [merge operation](cite:cites spec:rdf-semantics-1-2),
a near-union with blank-node renaming.
Because of the familiar nature of the dataset merge operation,
the operation is often not explicitly written when writing GAV mappings;
instead, mappings are often defined toword the global schema and implicitly merged.
This is a source of much confusion when talking about mappings over RDF since the
definition of mappings for each source, is a property often attributed to LAV.


**RML**

The RDF mapping language, [RML](cite:cites rml) and the standardized Relational to RDF Mapping Language [R2RML](cite:cites spec:r2rml) are declarative languages for describing mappings into RDF.
Each rule expresses one source's contribution;
the global graph is obtained by taking the dataset union of all rule outputs —
the same union-of-views construction described above.


**RML views.**

[The RML Logical Views module](cite:cites rml-lv, impl-rml-logical-view) of the
[modular RML spec](cite:cites rml-core) extends this with views defined over a single existing view or source, optionally joined with others.
RML thus remains aligned with knowledge graph *construction*: it does not support structural redefinitions across multiple sources, such as expressing a dataset
$$D$$ constructed from dataset
$$A, B \text{ and } C$$
such that $$D = (A \cup B) \setminus C$$.

**RML for RDF to RDF**

[POD-QUERY](cite:cites pod-query) uses RML to declare RDF-to-RDF mappings:
each rule names a single `rml:source` together with a query over it, and user queries against the global dataset are rewritten via standard [GAV unfolding](cite:cites lenzerini2002data).
Because the mappings are expressed in RML, POD-QUERY inherits its single-source limitation.
The reliance on RML is also a usability cost: RDF consumers typically know SPARQL, not RML.
Additionally,
POD-QUERY does not support RDF 1.2 and SPARQL 1.2 which requires special attention in unfolding.

**OBDA**


[Ontology-Based Data Access (OBDA)](cite:cites obda, obda-survay)
is a GAV instance in which the global schema is an ontology — typically expressed in DL-Lite_R,
the basis of OWL 2 QL — and the sources are usually relational databases connected through R2RML-style mappings.
Query answering in OBDA proceeds in two stages:
an ontology rewriting that reformulates the user query to capture facts entailed by the ontology's axioms,
followed by an unfolding step that uses the mappings to translate the rewritten query against the source schemas.
[Ontop](cite:cites ontop) is the reference open-source implementation;
Our approach shares the unfolding step with OBDA but addresses a different kind of heterogeneity.
OBDA reconciles semantic heterogeneity: sources that describe overlapping domains under different conceptualizations are aligned through an ontology.
The reification patterns we target express the same conceptual content — statements about statements — but encode it in different RDF structures.
We therefore do not require an ontology layer or its rewriting step; a single layer of CONSTRUCT-defined mappings driven by GAV unfolding suffices.
Put differently, OBDA relates concepts, while our rewriting relates structures.



**Positioning**

Our approach lets users declare mappings
<!-- -->
1. over multiple sources, through SPARQL federation;
2. in the SPARQL query language they already know; and 
3. using RDF 1.2 as both source and target.
<!-- -->
Federation matters here because it enables mappings that go beyond knowledge graph construction — including set-theoretic combinations across sources such as $$D = (A \cup B) \setminus C$$.
